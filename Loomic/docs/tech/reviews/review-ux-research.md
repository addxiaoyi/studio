# Helstera 桌面端 UX 研究设计（只读代码 · 无真机 GUI）

- 日期：2026-10-29
- 范围：`apps/web`（`/desktop-app/*` 渲染层 + 壳层组件 + 样式）、`apps/desktop`（Electron 主进程/preload）
- 方法：静态代码审读 + 既有测试断言清点。**未运行 Electron GUI，未采集任何用户数据。**
- 本文件是唯一写入物，未修改任何实现代码。

---

## 0. 结论先行（给 lead 的三句话）

1. **本轮交付的功能几乎都能被 jsdom 测试锁住"契约"，但没有任何一条证据能证明"用户会理解"。** 21 个 `apps/web/test/desktop-*.test.tsx` 覆盖了 toast 去重、连接态三态、焦点归还、roving tabindex —— 这些已是既成事实，研究不该再问"有没有"，只能问"看得懂吗"。
2. **统一反馈体系并不统一：toast 覆盖 8/8 模式，断线横幅只覆盖 4/8。** `desktop-app-page.tsx:436-445` 只在 `DesktopModule`（canvas/projects/assets/marketplace）挂横幅；home、mcp、development、settings 四个模式没有。这是代码可证的缺口，不是假设。
3. **最危险的不是"功能坏了"，而是"壳层存在两套"。** 侧栏导航（`desktop-workspace-sidebar.tsx:41`）跳到 `/desktop/?mode=X`，那是另一套旧壳（`app/desktop/page.tsx`，249 行，不含 toast/banner/空态/侧栏/标题栏）。而桌面主窗口入口是 `/desktop-app/`（`main.ts:3286`）。用户在哪儿、为什么会掉进旧壳、掉进去后是否以为产品坏了 —— 这是本轮最贵的不确定性。

## 1. 研究前提与证据分级

因为**无法运行 Electron 真机 GUI**，本报告所有判断按三级标注，任何读者都应先看等级再看结论：

| 等级 | 含义 | 谁能推翻它 |
| --- | --- | --- |
| **【代码可证】** | 静态代码/样式/测试断言能直接证明的确定事实。不需要用户。 | 只有改代码能推翻 |
| **【代码可推】** | 由代码事实推导出的合理结论，但中间含一步人因假设（如"8px 中文可读"）。 | 一次真人观察即可推翻 |
| **【需真人验证】** | 完全依赖真实用户行为/认知/设备环境，代码无法回答。 | 只有可用性测试能回答 |

**本次审读无法覆盖的部分（必须在结论里显式披露）**：

- 真机观感（毛玻璃/亚像素/字体渲染/DPR 缩放）、窗口拖拽缩放过程中的布局抖动；
- Electron 实际渲染与 Chromium headless 的差异（尤其 `titlebar` 拖拽区、`-webkit-app-region`）；
- 网络真实时延与断线抖动下的横幅时序；
- 已安装的客户端版本分布（`apps/desktop/package.json:3` 是 `0.2.18`，线上用户装的是哪个版本无从得知）。

### 3.2 需要重点说明的四条

#### (1) 系统状态可见性 —— 断线提醒有一半界面是哑的【代码可证】

- 横幅挂载：`desktop-app-page.tsx:436-445` `DesktopModule` 内，包住 canvas / projects / assets / marketplace。
- 缺失：`desktop-app-page.tsx:197`（settings 只包了 `DesktopToastProvider`）、`:428-433`（`DesktopAdvancedPage` 直接返回 `<main>`，mcp 与 development 都走它）、`:200`（home 只包 Provider）。
- 后果推演：用户停留在 **Agent 首页**（最核心的"创建任务"页）时断网，页面无任何横幅；此时点击"开始任务"只会得到一个 `role="alert"` 的错误段落（`:395`）或 toast，但那不是"我们掉线了，正在重连"这个语义。
- 横幅自身的时序设计是讲究的：首次连接静默（`desktop-connection-banner.tsx:44-49`）、恢复态只显示 2s（`:22`）、`navigator.onLine === false` 时升级为 `role="alert"`（`:71-78`）。**设计没问题，是覆盖范围没铺开。**

#### (2) 一致性与标准 —— 两套壳层并存【代码可证，本轮最高优先级】

这是我在复核中最意外的发现，也是"侧栏折叠后找回导航"这个测试任务的最大干扰项：

| 事实 | 证据 |
| --- | --- |
| 桌面主窗口入口是 `/desktop-app/`（安装后带 slug 时是 `/desktop-app/marketplace/`） | `main.ts:3286-3287` |
| 侧栏"项目/素材/MCP 工具/本地开发"点击后跳到 `/desktop/?mode=X` | `desktop-workspace-sidebar.tsx:40-44` |
| 标题栏导航全部指向 `/desktop-app/*` | `desktop-titlebar.tsx:62-76` |
| `/desktop` 是**另一套壳**：`DesktopCommandCenter`，249 行，**不引用** toast / banner / 空态 / 侧栏 / 标题栏任何组件 | `app/desktop/page.tsx`（grep 五个组件名 0 命中），`:168`、`:190`、`:220-221` |
| 侧栏挂在 `(workspace)/layout.tsx:79`，即仅工作区路由组可见；`/desktop-app/*` 与 `/desktop` 都**不含**侧栏 | `app/(workspace)/layout.tsx:79` |
| 标题栏挂在根布局，所有路由可见（含非桌面） | `app/layout.tsx:136` |

由此产生三个必须真人验证的问题（全是【需真人验证】）：
1. 用户点侧栏"项目"后落到旧壳，是否察觉"界面风格变了"？（旧壳无标题栏之外的任何壳层能力）
2. 侧栏在桌面主流程里到底会不会出现？入口是 `/desktop-app/`，那里没有侧栏；只有当用户进入 `/home/`、`/canvas/`、`/projects/` 等工作区路由时侧栏才出现。**这条路径是否存在、是否被用户走到，代码无法回答。**
3. 两个壳的"设置"是不同东西（`/desktop-app/settings/` vs `/settings/`）。

#### (3) 识别优于回忆 —— 默认折叠 + 8px 标签【代码可证 + 需真人验证】

- 默认 `collapsed: true`（`desktop-titlebar.tsx:93`），注释说明是为了与改造前 74px 窄轨一致。
- 折叠态标签样式：`max-width: 64px; font-size: 8px; white-space: nowrap; text-overflow: ellipsis`（`globals.css:142`）。展开态 12px（`:148`）。
- 折叠态单项最小高度 48px（`:139`），点击目标够大；**问题不在可点性，在可读性**：8px 中文在 100% 缩放下接近汉字可辨识下限，且 64px 宽度会把"本地开发"截断成省略号。
- 可访问性上标签是真实文本（不是 `display:none`），所以屏幕阅读器能读到；同时每项有 `title` 属性兜底。**语义没问题，视觉有问题。**

#### (4) 帮助识别/诊断/恢复错误 —— 去重窗口可能吞掉重复失败【代码可证】

`desktop-toast.tsx:37-50`：

```
key = toast.key ?? `${toast.tone ?? "info"}:${toast.message}`
if (now - lastAt < 5000) return;   // 静默丢弃
```

- 显式传 `key` 的地方做得对（`install:${id}`、`remove:${id}`、`download:list-failed:${reason}`）。
- 但**未传 key 的错误**（如 MCP 面板、设置页的通用失败文案）只要 `tone:message` 相同，**5s 内的第二次连击不会给任何新反馈**。用户在 5s 内第二次点同一个失败按钮，界面看起来"没反应"。
- 另外 `recentKeys` Map 只增不删（`:31`、`:43`），长期会话下无限增长——不是 UX 问题，但是同类缺陷。
- `role="status" aria-live="polite"`（`:57`）：**错误也是 polite**，屏幕阅读器不会打断当前朗读。4s 内需读完的错误信息，对读屏用户偏紧（WCAG 2.2.1 时控关注点）。

| A13 | 焦点归还符合用户预期（Esc/Ctrl+K 关闭后回到触发元素） | jsdom 已断言（`desktop-titlebar.test.tsx:342/361`） | 只影响键盘用户，影响面小但一旦错就是"焦点丢失在地" | 低 | A1 顺带 |
| A14 | 4 个执行方式（隔离浏览器/授权标签页/本机应用/视觉 OCR）用户能选对 | 每个模式都有 hint 与连接前置校验（`desktop-app-page.tsx:391`、`:398`） | 选错模式导致任务在错误执行器上失败，用户归因为"产品不能用" | 中高 | T1 观察点：是否读 hint、是否选错 |

## 5. 可用性测试方案（可直接执行）

### 5.1 通用设置

| 项 | 设定 | 理由 |
| --- | --- | --- |
| 被试 | 5 人：3 名中国创作者（有 AI 工具使用经验）、1 名设计/运营（低技术背景）、1 名开发背景 | 5 人可暴露约 80% 的严重可用性问题；覆盖技术梯度 |
| 会话 | 1 对 1 远程主持，每人 45 分钟，出声思维 | 远程可共享屏幕看真实窗口尺寸 |
| 环境 A（必做） | **预装 0.2.18 的客户端**，窗口手动拉到 **720×480**（最小尺寸） | 直接压测 A2/A5；且验证 ui 在小窗口的真实表现 |
| 环境 B（选做 2 人） | 1280×800 默认窗口 | 对照，分离"小窗口问题"与"通用问题" |
| 记录 | 屏幕录制 + 音频 + 主持笔记；外部行为以**URL 变化**为主要客观信号（见 A9） | 用户嘴上说的不可靠，URL 不会说谎 |
| 前置 | 被试已登录、有至少 1 个已安装扩展、MCP 列表**至少 1 个连接失败的条目** | 避免现场造数据 |
| 伦理 | 明示"测产品不是测你"，可随时退出；不录屏给第三方 | — |

**主持原则**：任务描述只念一遍，不追加提示；用户提问时回答"你觉得呢？"；卡住超过 **90 秒**才给 1 级提示（"看看左侧"），超过 **3 分钟**记为失败并进入下一任务。

### 5.2 五个任务

#### T1 · 首次创建任务（覆盖 A14、A7）

| 项 | 内容 |
| --- | --- |
| 场景铺垫 | "你刚装好 Helstera，想让 Agent 帮你把一个网站介绍清楚。" |
| 任务原文（照念） | "请让 Agent 帮你整理一个你熟悉的网站的介绍，并把它跑起来。" |
| 成功判据 | ①在 Agent 首页找到输入框并提交；②显式选择了一个执行方式；③任务开始后能看到运行中的状态 |
| 观察点 | 是否读模式 hint；**首次点击是否落在 4 个执行方式按钮上**（默认已选"隔离浏览器"，用户是否注意到默认值）；提交前是否尝试找"保存"之类不存在的按钮；断网提示缺失时是否察觉（配合 T5） |
| 预计耗时 | 5–8 分钟（含出声思维） |

#### T2 · MCP 连接失败恢复（覆盖 A8、A3）

| 项 | 内容 |
| --- | --- |
| 前置 | MCP 列表里存在 1 个"连接失败"的服务器（真实失败，不要伪造文案） |

| 观察点 | 是否把"连接失败"误读为"未连接"；**5s 内连点两次时的界面反应**（记 A3）；失败原因文案是否读完；是否去别处找日志 |
| 预计耗时 | 6–10 分钟 |

#### T3 · 侧栏折叠后找回导航（覆盖 A1、A5、A6、A9 —— 最高价值）

| 项 | 内容 |
| --- | --- |
| 前置 | 侧栏为默认折叠态 |
| 任务原文 | "请回到'项目'列表。" |
| 成功判据 | ①找到并点击侧栏"高级能力"分组；②点中"项目"；③到达项目页且**没有把页面搞乱** |
| 观察点 | **记录每一次 URL 变化**（尤其是否掉进 `/desktop/?mode=projects`）；是否把标题栏的"项目"（`/desktop-app/projects/`）与侧栏的"项目"（`/desktop/?mode=projects`）当成同一个；折叠态 8px 标签是否被读出来（出声复述）；是否使用键盘 |
| 预计耗时 | 4–8 分钟 |
| 特殊记录 | 若落到旧壳后用户说"页面变了/没反应了/加载好慢" → A9 命中，严重度升级 |

#### T4 · 市场安装一个已被下架的插件（覆盖 A11、A12）

| 项 | 内容 |
| --- | --- |

| 成功判据 | ①切到"已安装"tab；②看到"已下架"徽标与"该插件已下架，请更新或移除"；③完成移除 |
| 观察点 | 在发现页搜不到时是否以为"搜错了"；是否注意到"已下架"徽标（8px 级小字？实际是普通徽标）；遇到 `window.confirm` 系统弹窗时的反应（是否怀疑是钓鱼弹窗）；移除后的成功 toast 是否被注意到（4s） |

#### T5 · 断网后继续操作（覆盖 A7、A3）

| 项 | 内容 |
| --- | --- |

| 任务原文 | "网络好像有点问题，你先照常开始一个任务看看。" |
| 成功判据 | ①用户明确说"连不上/断网了"（而不是"按钮坏了"）；②恢复网络后能继续 |

| 预计耗时 | 5–8 分钟 |

## 6. 度量与埋点建议

**现状**：web 侧只有两条上行通道——错误上报 `navigator.sendBeacon("/api/errors")`（`lib/error-reporter.ts:123-134`）与 Web Vitals（`lib/web-vitals.ts:211-215`）。**没有产品行为埋点**（无 posthog/gtag/自定义 track）。桌面壳侧有 Electron 日志。

| # | 指标 | 定义 | 采集成本 | 落地方式 |
| --- | --- | --- | --- | --- |
| M1 | 任务创建成功率 | 首页提交次数 / 成功进入运行态次数 | **需新增** | 两个事件：`agent_task_submit`、`agent_task_started`；无后端改动可在 web 层打 |
| M2 | 首次任务创建耗时 | 首页可交互 → 提交成功 | **需新增** | 随 M1 附 `performance.now()` 差 |
| M3 | 错误恢复时间 | 首次失败提示出现 → 下一次成功操作 | **需新增 + 已有部分** | 前端打 `error_shown` / `error_resolved`；`/api/errors` 已有错误率基座，可算"同会话错误簇" |
| M4 | toast 被真实阅读率（代理指标） | toast 出现 → 4s 内是否有关闭/后续点击行为 | **需新增** | `toast_shown` / `toast_dismissed{reason:auto\|manual}`；注意：**真实阅读只能人工观察** |
| M5 | toast 去重吞掉的事件数 | 被 dedupe 丢弃的 push 次数 | **需新增（成本极低）** | 在 `desktop-toast.tsx:42` 的早返回处计数上报；**这是验证 A3 最便宜的客观数据** |
| M6 | 断线期间的状态可见覆盖率 | 处于断线且当前模式 ∈ {home,mcp,development,settings} 的会话占比 | **需新增 + 需要先补横幅** | 上报 `mode` + `realtime_status`；先修覆盖率才有意义 |
| M7 | 侧栏导航去向分布 | 侧栏点击后落到 `/desktop` vs `/desktop-app` 的比例 | **需新增** | `nav_click{from:"sidebar",to:pathname}`；**这是量化 A9 的唯一客观手段** |
| M8 | MCP 连接失败率 / 重试成功率 | 失败次数、重试后成功比例 | **已有部分** | 现有 `/api/errors` 能捞到失败；重试语义需新增 |
| M9 | 市场安装失败率 / 下架条目占比 | — | **已有（服务端）** | 服务端已有 installs 与 market 数据，可直接算 |

**采集红线（建议写进需求）**：不上报任何 prompt 正文、工具参数、文件名；`mode`/`pathname`/`tone`/`reason` 这类枚举足够。桌面端涉及本机操作，埋点必须可一键关闭。

### 7.2 建议先测的 3 条

1. **T3（侧栏折叠找回导航）** —— 一次性覆盖排名 1 和 3 的两大未知，且是唯一能证伪"用户在旧壳里迷路"的实验。
2. **A3（toast 去重吞错）** —— 不必等真人：先在 `desktop-toast.tsx` 的丢弃分支加一个计数上报（M5），**一周内就能拿到"每天被吞掉多少条反馈"的硬数字**；若数字不为 0，再进 T2/T5 补人因证据。
3. **A7（首页断线无提示）** —— 这不是研究问题而是**缺陷**。建议直接进修复清单，研究只做一件事：在 T5 里确认"用户会把断网误判成产品 bug"（用来给修复排优先级）。

### 7.3 建议的第一个实验（可直接开跑）

> **实验 E1：折叠态导航可发现性 + 旧壳迷失率**
>
> - **怎么做**：5 名被试 × 1 小时远程主持，环境 A（0.2.18，窗口 720×480，侧栏默认折叠）。只跑 **T3**，用户出声思维；主持人只记录不动手。全程录屏 + 采集 URL 轨迹。
> - **看什么指标**：①**T3 任务成功率**（目标：≥4/6 独立完成，首次点击即命中侧栏分组）；②**旧壳误入率**＝落到 `/desktop/` 的被试比例；③**8px 标签复述正确率**（用户能否念出"项目/素材/MCP 工具/本地开发"）；④**求助次数**与首次提示时间。
> - **多久出结论**：招募 2 天 + 执行 1 天 + 分析 1 天 = **4 个工作日**。5 人样本只给方向性判断（"3/5 读不出标签"就是信号），不做显著性检验。
> - **判定门槛**：若旧壳误入率 ≥ 2/5 **或** 标签复述正确率 < 3/5 → 判定为 P0，进入修复（统一导航到 `/desktop-app/*`，折叠态加 Tooltip 或提高字号）。
